This document analyzes Scribe-specific security properties, focusing on how
Scribe uses Tributary's secondary stream mechanism for libraries and write access
sharing. It supplements the [core Tributary security document](../../../docs/security.md),
which covers the underlying cryptographic design, threat model, and protocol.

Readers should be familiar with the core document before reading this one.

## Library Architecture

Scribe organizes user data into **libraries**, each backed by a Tributary
stream. A user has one **home library** (backed by the password-derived root
stream) and zero or more **secondary libraries** (backed by randomly generated
keypairs).

```
Home library (root stream, password-derived)
├── collection: "Recipes"   → linked_stream_id, linked_stream_key
├── collection: "Work Notes" → linked_stream_id, linked_stream_key
└── collection: "Journal"    → linked_stream_id, linked_stream_key
```

Each linked collection stores a pointer (`linked_stream_id`) and the full
Ed25519 private key (`linked_stream_key`) for the secondary library.

## Secondary Key Generation

Secondary library keypairs are generated randomly via `nacl.sign.keyPair()`
(TweetNaCl's CSPRNG-backed Ed25519 key generation). They are **not** derived
from the user's password and cannot be recovered from password alone.

**Implementation:** `apps/scribe/scribe-data/src/library.ts` (`createLibrary`).

## Secondary Key Storage

Secondary private keys are stored as base64url-encoded strings in the
`linked_stream_key` column of the `collection` table within the home library's
stream.

Because the home library is a Tributary stream, all writes to the `collection`
table -- including the `linked_stream_key` values -- go through the standard
encryption pipeline:

1. The SQL `INSERT` is serialized to JSON.
2. The JSON is encrypted with XSalsa20-Poly1305 using the home stream's
   symmetric key (derived from the home stream's Ed25519 private key).
3. The encrypted blob is signed and uploaded to the server.

The server therefore stores secondary private keys only as opaque ciphertext
within the home stream's encrypted blobs. An attacker with full server database
access cannot extract secondary keys without first compromising the home
stream's private key (which requires the user's password).

**Implementation:**
- Storage: `apps/scribe/scribe-data/src/library.ts` (`createLibrary`, lines 70-76)
- Schema: `apps/scribe/scribe-data/src/migrations.ts` (`syncedMigrations`, lines 30-40)

## Write Access Sharing

Scribe allows sharing write access to a secondary library by transmitting the
full Ed25519 private key to another user. The current mechanism encodes the
private key in a URL:

```
yourapp.com/#/import/write/{base64url_encoded_secret_key}
```

The recipient's client decodes the key, registers it locally via
`client.addWriteKey()`, and syncs the library's encrypted blobs from the server.

**Implementation:**
- URL handling: `apps/scribe/scribe-react/src/pages/ImportLibraryPage.tsx`
- Import logic: `apps/scribe/scribe-data/src/library.ts` (`importLibrary`)

### Security Properties of URL-Based Sharing

Embedding the private key in a URL has known trade-offs:

| Property | Status |
|---|---|
| Key protected in transit (HTTPS) | Yes, assuming HTTPS |
| Key visible in browser history | Yes -- risk |
| Key visible in HTTP Referer headers | Possible if the page links to external resources |
| Key logged by chat/email systems | Yes, if the URL is shared via a logged medium |
| Key persists in server logs | The fragment (`#/import/...`) is not sent to the server in standard HTTP requests, but may be logged by client-side analytics or error reporting |

The URL fragment (`#/import/write/...`) is never sent to the Tributary or
Supabase server as part of normal HTTP requests. However, once the key reaches
the recipient, it is stored in their local PGLite database (in the
`tributary.streams` table) without additional encryption, consistent with
Tributary's threat model exclusion of device compromise.

### Auditor Checklist for Sharing

1. Verify that the URL format uses a fragment (`#/import/...`) rather than a
   query parameter or path, so the key is not included in server-side HTTP logs.
2. Verify that the import page does not send the private key to any analytics,
   error reporting, or third-party service.
3. Verify that after import, the private key is stored only in the local PGLite
   `tributary.streams` table and not persisted elsewhere (e.g., `localStorage`,
   cookies, or session storage).

## Blast Radius Analysis

| Compromise Scenario | Impact |
|---|---|
| Single secondary key leaked | Only that library's data is exposed. Home library and other secondary libraries are unaffected. |
| Home stream key compromised (password) | All secondary keys stored in the home stream are exposed, giving access to all linked libraries. |
| Shared URL intercepted | The interceptor gains full read+write access to the shared library. Other libraries are unaffected. |
| Server database breach | No plaintext is exposed. Secondary keys are encrypted within home stream blobs. |

## Known Limitations

- **No read-only sharing.** Scribe currently shares the full Ed25519 private key,
  granting both read and write access. The Tributary protocol's separation of
  signing key and encryption key would allow read-only grants (share only the
  symmetric encryption key), but this is not yet implemented.

- **No key revocation for shared libraries.** Once a private key has been shared,
  the recipient retains access permanently. There is no mechanism to rotate a
  secondary stream's keypair and re-encrypt its history.

- **URL sharing is a one-time operation.** The URL itself is not tied to a
  session or expiry. Anyone who obtains the URL at any point in time gains
  permanent write access.
